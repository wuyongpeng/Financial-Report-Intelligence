# 财报智析台：冲刺比赛整体评审

评审时间：2026-09-09。范围：当前工作区（含未提交修改）、本机数据库、现有测试及项目文档。已根据用户补充的《上市公司财报智析：数据直通与智能问答》课题说明校准优先级；尚无评分权重和提交截止时间，本评审不预测获奖概率。数据库结果只代表本机，不能据此断言线上环境一致。

## 依据课题说明校准的优先级

核心主张应是：为热门上市公司建立可主动调度、可监测的财报直通通道，并让用户从经营变化追溯到真实原文。验收分成“数据到达”和“用户用起来”两条流程。

| 课题要求 | 当前证据 | 下一步验收 |
|---|---|---|
| 至少 50 家财报数据、四项核心指标 | 本机仅 4 家具备完整核心指标 | 逐公司检查实际可阅读财报、四项指标和原文；名单数量不作完成数 |
| 交易所公开渠道直通，可多源兜底 | 三源代码已实现，尚未验证密集期发现完整性 | 连续运行记录发现、下载、解析、可用时间，测试单源故障和积压恢复 |
| T+0 日内上线 | 已有部分时间字段，无完整达标报表 | 按北京时间公告当日统计可用比例，记录失败及跨日原因 |
| 评委通过线上链接独立走通 | 本次未做线上或浏览器交互验收 | 普通用户从入口完成选报告、图表、正确章节、问答与引用定位 |
| 手机 C 端、桌面研究场景 | 有响应式切换与研究工作区代码 | 分别完成手机速读任务和桌面多期、同业任务；不能仅以 CSS 存在认定通过 |
| 问答准确率以人工审核为准 | 24 个题目但未逐题审核评分 | 固定真实问题集、保留模型答案、人工判断和引用依据，输出失败案例 |
| 使用说明与技术文档 | 已有文档，部分内容落后于实现 | 与最终行为、访问地址、数据范围和质量报告保持一致 |

明确区分：50 家覆盖、核心指标、线上完整流程和人工审核的问答准确率来自赛题；“50 家所有指标都人工复核”“8 家各四期”来自项目自设验收，不是赛题明示的硬门槛。不能把这些内部增强目标混作官方要求。人工问答评测与生产指标逐条复核也不是同一个流程。

### 新增最高优先级发现：公告发现完整性

主采集函数只调用三源第一页（请求 pageSize=200），没有遍历分页，再在本地筛选 50 家公司。密集披露期，目标公告若落在后续页，将无法被这一轮发现。多源都只查第一页不能保证补齐这类漏报。

- 位置：[源查询与分页](/Users/yongpeng3/src/financeAnalysis/lib/sources.ts:33)、[主入口](/Users/yongpeng3/src/financeAnalysis/lib/sources.ts:98)。
- 修改：在来源支持范围内按标的、时间窗口或分页遍历，保存采集水位，使用时间重叠与去重处理延迟到达、修订公告和重启补漏；设置低频请求、退避和独立源状态。
- 验收：用本地可控公告列表模拟目标公告位于第二页及以后，验证无漏报、无重复；再用实际运行日志验证来源可用性。此结论来自代码检查，本次没有据此断言已经发生线上漏报。

### 新增最高优先级任务：证明 T+0，并保护新公告处理能力

默认每 10 分钟最多下载 5 份、解析 3 份。仅按数量上限估算，解析能力约 18 份/小时；实际吞吐还受文件大小、解析耗时和失败影响。白天积压与临近午夜到达的公告不能用同一份静态样本演示证明日内可用。

- 保留源站低频发现，已归档文件的本地解析按有界并发持续消化，避免新公告必须与历史回填共用固定小批次配额。
- 新公告、历史回填、失败重试应有独立优先级和公平调度；需要退避、失败隔离、重启恢复和积压最老年龄。
- 当前 `online_at` 由管理员批准写入，而 `review` 数据实际上已可阅读。需要明确定义“用户首次可用”与“人工已复核”，分别记录 `available_at`、`verified_at`，不能混用来计算 T+0。自动可用应有明确质量门槛，并展示核验状态。
- 上交所代码把公告日期补为零点，因此该时间不能用于声称分钟级发布延迟。保存源时间精度；只有日期时计算日内达标，发现到可用耗时可单独精确测量。
- 历史导入与实时新公告分组统计，不能把回填时间当成实时发现性能。没有原接收机链路的实际时延数据时，只报告新路径的实测性能，不声称已经快于旧路径若干倍。

建议增加简洁的“数据直通状态”入口，展示目标覆盖数、实际可用公司数、来源、最后成功采集、积压、当日可用率和异常；详情页展示该报告来源及可用时间。面向 C 端的主页面仍以读懂财报为主。

### 覆盖扩大后的入口风险

首页请求最新 100 份公告，随后才在客户端按公司聚合。扩展到 50 家、多报告期及持续新增公告后，不能保证所有已覆盖公司都落在这 100 份里；未出现的公司可能被显示为“财报准备中”。应把公司列表及每家公司最新可用报告的查询放在服务端，按公司分页；历史在进入公司后独立加载。

- 位置：[报告列表限制](/Users/yongpeng3/src/financeAnalysis/app/api/reports/route.ts:13)、[首页请求](/Users/yongpeng3/src/financeAnalysis/app/page.tsx:51)。
- `/api/status` 中的 coverage 目前也是静态名单长度，应与实际可用覆盖区分。

### 两类用户的获益应分别验证

- 手机速读：公司搜索、三条可核验要点、四项指标和简洁趋势优先；点引用可以读清原文并方便返回；推荐问题必须落在可用数据范围。用普通用户能否独立完成任务验收，不能只检查布局是否缩小。
- 桌面研究：选择同口径报告期、对照同期同行、持续追问与查看跨报告证据。优先让现有比较工具和问答共享相同数据上下文。

增强指标、业务分部图及更复杂归因放在上述硬要求之后。研究深度可以先由少量完整案例展示，但不能替代 50 家基本覆盖。

## 总体判断

项目已有真实公告采集、PDF 归档、规则解析、图表、原文定位、问答及管理员复核，具备完整产品形态。比较有价值的方向是“从经营变化追到可核验的证据”。接下来应优先提高这条流程的正确性和完整性，并形成可复现的评测结果。

建议保留的设计：来源与分析联动；缺数据不生成替代数字；同类型报告的历史比较；明确标注机器解析和人工复核；模型不可用时保留基本阅读能力。

## 第一优先级：先修正确性与闭环

### 1. 新增指标与“完整报告”判定冲突

解析器已支持八项指标，首页仍使用 `metrics.length === 4`；采集状态和 P0 验收也有相同假设。一旦补录辅助指标，四项核心指标完整的报告可能从首页消失，并被标成部分解析。目前数据库只有四项指标，因此这是确定的代码缺陷，但尚未在当前数据中触发隐藏。

- 位置：[首页过滤](/Users/yongpeng3/src/financeAnalysis/app/report-home.tsx:17)、[采集状态](/Users/yongpeng3/src/financeAnalysis/lib/ingest.ts:193)、[验收计数](/Users/yongpeng3/src/financeAnalysis/scripts/p0-audit.ts:13)。
- 修改：用核心指标名称集合判断完整性；核心完整度、辅助指标覆盖和人工复核分别计数，统一复用一处判定。
- 验收：含 4、5、8 项指标且核心齐全的报告均可阅读；数量恰好为 4 但缺少某个核心指标的报告不能算完整。

### 2. 章节定位命中目录或交叉引用

`buildOutline` 取章节关键词首次出现的页面。本机数据已复现：茅台的 mda 指向 PDF 第 2 页“重要提示”；招行指向 PDF 第 2 页目录，而其管理层讨论正文从 PDF 第 11 页开始。详情页又截取该页前 420 字作为“公司自述”，使问题直接呈现在分析模块中。

- 位置：[章节定位](/Users/yongpeng3/src/financeAnalysis/lib/outline.ts:35)、[公司自述取文](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:270)。
- 修改：区分目录、交叉引用和正文标题；利用 PDF 书签或目录解析辅助定位，结合标题形态及正文长度评分；保存章节起止页。
- 验收：黄金样本的“管理层讨论、财务报表、风险”均跳转正文；公司自述必须与对应分析主题相关。

### 3. 成本字段与括号数字解析存在可复现错误

本地构造样例验证：

- 输入“营业收入 100000、营业总成本 80000、营业成本 60000”，`operating_cost` 取到 80000，来源为“营业总成本”。下游却将它直接代入标为“营业成本”的毛利率公式，结果为 20%，使用该样例营业成本应为 40%。
- 输入“经营活动产生的现金流量净额 (500000) 1000000”，解析器返回 1000000。开头括号数字被作为脚注移除，导致跳到后一列。

以上是构造输入的解析缺陷复现，不是对当前真实财报金额出错的断言。

- 位置：[字段定义](/Users/yongpeng3/src/financeAnalysis/lib/parser.ts:33)、[数字提取](/Users/yongpeng3/src/financeAnalysis/lib/parser.ts:51)、[毛利率计算](/Users/yongpeng3/src/financeAnalysis/lib/detail-model.ts:38)。
- 修改：分开营业成本与营业总成本；识别表头、本期/上期、合并/母公司口径、单位与括号数值；对冲突候选保留依据并进入复核。
- 验收：同一份真实报表逐行对照，新增指标有独立真值；核心指标未变不能被当成新增指标正确的证据。

### 4. 对话历史没有进入回答请求，同业数据也未接通

前端保存并展示多轮对话，但请求 `/api/chat` 时只发送本次问题和 reportId。后端也没有读取会话历史。用户追问“为什么？”或“那另一家呢？”时，模型无法获得前文所指。

同业分析 API 已能返回数值，问答 API 则只获取同行公司名称与代码。点击雷达“问这张图”只传入覆盖家数，不能支持可靠的排名解释。历史趋势按钮把展示值拼在问题字符串中，服务端没有以对应报告 ID 重建比较证据，引用仍只属于当前报告。

- 位置：[问答请求](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:344)、[后端上下文](/Users/yongpeng3/src/financeAnalysis/app/api/chat/route.ts:163)、[雷达追问](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:409)。
- 修改：传入有长度限制的会话上下文；明确当前报告、对比报告和同业对象；服务端从数据库加载真实比较值。跨报告引用包含 reportId、period、page、quote，而不只是 page。
- 验收：连续完成“本期利润变化是什么→为什么→和上年相比呢→和同行相比呢”，每一步使用正确公司、报告期与可打开的证据。

### 5. 自选基准仍被标为同比，不同模块口径不一致

选择早于上年同期的报告后，指标卡、异常提示和瀑布图仍使用“同比”或“上年同期”文案；关键发现则独立调用 `priorYear`，继续使用真正的上年同期。同一屏可能同时出现两套比较基准。

- 位置：[对比基准](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:239)、[关键发现](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:268)、[同比标签](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:393)。
- 修改：建立统一 comparison context，显式包含基期与比较类型；只有上年同报告期才标“同比”。如关键发现固定采用同比，必须明确说明它不随自选基准变化。
- 验收：切换到两年前报告后，卡片、分解、异常、摘要和问答的基期清晰且一致。

### 6. PDF 原文阅读重复下载与解析整份文件

`PdfEvidence` 的 effect 依赖 reportId、page、quote；父组件的 key 也包含页码和引用。每次换页或换引用都会重新获取完整 PDF 并建立解析对象。HTTP 缓存可能减少网络传输，但不会消除反复读取与解析的工作。

- 位置：[PDF 生命周期](/Users/yongpeng3/src/financeAnalysis/app/pdf-evidence.tsx:16)、[组件 key](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:384)。
- 修改：按 reportId 复用 PDF 文档对象；页面渲染与高亮分离；缓存当前页和临近页，并在离开报告时释放资源。
- 验收：连续点击十次引用，记录文档加载次数、定位耗时和内存；切页时不重建同一文档。

## 第二优先级：让核心功能有足够真实数据

1. 修正完整度判定后，再回填八项指标。当前积压查询主要处理未下载、待解析或缺少 chunks 的报告；已经有 chunks 的旧报告不会仅因解析器升级而自动补齐新字段。增加解析器版本和可恢复的重解析入口，保留前后差异。
2. 完成八家黄金样本的同类型四期数据，再扩大覆盖；如果比赛明确要求 50 家，则把该要求作为硬门槛。公司名单、已发现公告、可阅读报告、已复核报告分别统计。
3. 当前 2026H1 食品饮料和银行各只有两家公司可比较。两点百分位自然容易落到 0/100，信息量有限；小样本优先展示两家公司数值差异，样本足够后再强调分布和百分位。
4. 主营业务构成模块目前明确未解析。若它是比赛核心能力，应对黄金样本完成真实分部数据；否则减少首屏入口的重要性，避免推荐问题把评委引向未完成的功能。
5. 核验状态应绑定数据版本。当前重解析更新指标时不重置 verified；管理员批准又一次性标记该报告所有指标。应支持逐项核验，并在数值、单位或口径变化后撤销相应旧核验。
6. 反馈中的 reporter 当前只区分 user/guest，同角色访问者会覆盖同一条反馈。应使用独立匿名会话 ID 或用户 ID，再讨论累计确认数与优先复核队列。

## 第三优先级：建立可展示、可重跑的评测

把“24 个问题已存在”升级为“逐题有期望结果、有引用、有运行结果”。建议评测覆盖：

| 维度 | 检查内容 |
|---|---|
| 数字 | 金额、单位、正负号、报告期、同比计算；接受等价单位和合理舍入 |
| 引用 | 引用页存在，引用片段存在，片段支持该条结论；跨报告来源准确 |
| 问答 | 原因、业务、风险、多轮指代、历史比较、同业比较 |
| 边界 | 缺少数据、不存在年份、未覆盖公司、无法检索的页面 |
| 稳定性 | 超时、流中断、模型不可用、切换报告后的旧请求取消 |
| 使用效果 | 完成同一个任务的耗时、正确率、引用定位操作次数 |

保留未参与开发调试的测试样本；区分各行业和版式；输出失败案例，不只展示总平均值。解析器的启发式 confidence 不能直接解释为经过校准的“正确概率”。

可以设内部目标，但不要把目标写成已经达到的成绩。具体阈值应结合比赛评分表、模型环境和实测结果制定。

## 产品定位与答辩材料

建议围绕一个明确工作任务组织演示：“发现利润变化，比较历史与同行，找到管理层解释，定位原文并核验。”这条链路比逐一介绍所有模块更容易让评委判断实际价值。
