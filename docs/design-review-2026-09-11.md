- 产品主张“问财报，有出处”明确。公司、报告期、指标、趋势、原文与问答围绕同一任务组织，比孤立的聊天入口有价值。

- 后端已拆出检索、回答、会话和指标判定模块；引用包含报告 ID、公司、报告期、页码；支持引用编号校验、回答中断状态与降级。这些是实质性工程资产。
- 9 月 9 日提出的核心指标按名称判断、发现分页、会话隔离、括号金额解析、营业成本字段和章节定位等问题，已出现针对性实现与测试。不能把这几天的工作归结为只改样式；真实 PDF 的广泛准确性仍要单独验证。

**3. 优先级最高的具体问题**

**P0：采集失败中存在确定的运行时类型错误。**

数据库已有中国石油失败记录：`TypeError: publishedAt.slice is not a function`。本次只读确认 PostgreSQL 返回的 `published_at` 实际是 Date；`lib/ingest.ts` 却把它声明成 string。`periodFromTitle` 的年份匹配要求 `2026年` 连写，当标题是实际存在的 `2026 年` 时进入 `publishedAt.slice` 分支并失败。捕获逻辑又把解析异常统一记成 download_failed。

修改目标：在数据库到领域模型的边界规范日期；年份解析接受空格；区分下载失败与解析失败。验收应包含这一真实标题和 PostgreSQL 的 Date 返回值，并证明相同报告无需重复下载即可继续解析。

证据：[日期解析](/Users/yongpeng3/src/financeAnalysis/lib/ingest.ts:37)、[处理积压](/Users/yongpeng3/src/financeAnalysis/lib/ingest.ts:113)。

**P0：目标池有多个事实来源，新增监控在部署后不可靠。**

新增公司接口写 `data/companies.json` 和数据库，但 Worker 使用模块加载时静态导入的 JSON 和 Map；每轮 bootstrap 又把不在该静态列表中的公司设为 disabled。Docker 中 app 与 worker 是独立容器，仅共享 PDF 目录，并不共享这个 JSON 文件。即便 app 写文件成功，也不能保证运行中的 worker 接受新公司。

修改目标：以数据库作为运行时监控名单，JSON 仅用于首次初始化；新增监控、发现过滤、启停、采集和页面统一查询数据库。验收：新增公司后，无需重启、重新构建或手工编辑文件，即可被 Worker 识别；重启后仍保留。

证据：[新增监控](/Users/yongpeng3/src/financeAnalysis/app/api/companies/watch/route.ts:55)、[静态监控池](/Users/yongpeng3/src/financeAnalysis/lib/ingest.ts:11)、[启停重置](/Users/yongpeng3/src/financeAnalysis/lib/ingest.ts:60)、[部署挂载](/Users/yongpeng3/src/financeAnalysis/docker-compose.yml)。

**P0：普通访客的多轮记忆没有形成闭环。**

首页无需登录即可进入；创建持久会话要求有效登录，失败后前端继续发无 conversationId 的问题。后端只在提供 conversationId 时加载历史。因此访客能看到前面的气泡，但“为什么？”等追问没有历史输入。跨报告期切换时，界面可以保留旧气泡，后端会话仍按单份报告绑定，也需明确上下文边界。

修改目标：为普通访客建立受限且隔离的会话身份，或明确要求登录；不要在不具备记忆时表现为有记忆。验收必须从新的未登录浏览器开始，连续完成“利润怎么变了 → 为什么 → 与去年相比 → 与同行相比”，检查每轮实际使用的公司、期间和证据。

证据：[前端匿名降级](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:683)、[后端历史加载条件](/Users/yongpeng3/src/financeAnalysis/app/api/chat/route.ts:25)、[会话创建权限](/Users/yongpeng3/src/financeAnalysis/app/api/conversations/route.ts:27)。

**P0：存在没有可见收益的模型调用。**

详情组件进入或切换报告时自动请求三句话 AI 概览，返回结果写入 summary，但 summary 和 summaryBusy 未在渲染中使用；lint 同时报告它们未使用。回答结束后还会再调用模型生成推荐追问，即使主问题是无需模型的结构化查询。问答和追问端点没有统一请求配额或成本预算。

修改目标：取消无展示用途的概览请求，或只在确有用途时生成并按报告版本缓存；推荐追问优先基于现有数据模板生成；为调用用途、模型、token、耗时、缓存命中和失败记录成本。公开问答应有服务端预算限制。

证据：[未使用状态](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:122)、[自动概览](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:214)、[每轮追问](/Users/yongpeng3/src/financeAnalysis/app/company-detail.tsx:705)、[追问模型请求](/Users/yongpeng3/src/financeAnalysis/app/api/chat/followups/route.ts:35)。这里说的是产品运行时模型费用，与用户已经花掉的 Cursor 开发额度是两笔不同的账；本次没有 Cursor 账单，无法计算历史费用是否合理。

**P1：可用、已解析、已入库、已复核的口径没有统一。**

`audit:p0` 的核心覆盖包含停用公司；`/api/status` 检查核心完整且有原文索引；`/api/crawl` 取最新公告，界面以存在任何指标判为可读。最新公告未解析时，也可能掩盖同公司的旧可用报告。数据源页“已入库”使用 online 数量，当前显示 0，却同时显示 5 家已覆盖；“并发槽位”则根据一次 run 是否 running 推算，参数本身是每轮处理数量，不是真实并发任务数。

修改目标：统一“目标公司、已发现、PDF 已归档、核心完整、原文可检索、人工复核”的定义；明确展示最新公告和最新可用报告；用真实任务状态展示 Worker 活跃与积压，区分开关开启与进程存活。

本机 `ingest_runs`、`source_health` 为空，不等于从未手工导入或处理数据，但意味着没有完整轮询实测证据。应记录运行心跳、阶段时间、失败、积压年龄、首次可用时间。只有源日期时，不能据此计算分钟级公告发布延迟。

**P1：引用存在不等于结论受支持。**

`validateCitations` 主要检查引用编号是否属于本轮证据，无法判断该段证据是否支持对应结论。检索主要是中文词片段、领域关键词和页级排序；历史与同行结构化指标已接入，但原文 chunks 仍只检索当前报告。

修改目标：把现有 24 题变成有预期数字、期间、引用和人工判断的评测；加入访客追问、负数、缺数据、跨报告、同业问题。先从失败案例判断是否需要更细分块、全文索引、语义检索或重排，避免未经测量直接增加向量库和模型调用。

**P1：首页完成感低于实际能力，详情组件的修改风险正在上升。**

本次浏览器首屏是一整片等待抓取的公司；真正可读样本在列表后面。建议默认突出可读公司，提供明确可执行的问题示例；待抓取公司仍可搜索，但不占据主要首次体验。当前公司详情约 902 行、首页约 803 行、采集页面约 779 行，数据加载、会话、PDF、拖拽、分析和展示混杂。PDF 的加载 effect 仍依赖报告、页码和引用，换页会重新建立文档解析对象。

修改目标：先冻结整体布局；围绕实际要修的问题拆出会话控制、PDF 生命周期和报告查询，不做全项目重写。复用同一报告的 PDF 文档，页面渲染与高亮独立。现有 Next/VM 与早期 Vinext/Cloudflare 的配置并存，可在交付路径稳定后清理未用部分。
