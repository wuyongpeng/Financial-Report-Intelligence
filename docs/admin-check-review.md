# 指标核对：审核与处理进度

`/admin/check` 末列按顺序提供「解析 / 审核通过 / 标记异常 / 已处理」。解析复用 `/api/crawl/trigger` 的单报告 immediate parse 路径；同报告请求中禁重复点击，完成后可再次解析。请求接受不等于成功完成；界面根据报告状态和 parsed_at 确认完成后刷新核对结果，最多监测五分钟，超时明确提示手动刷新，不自动重发。

## 两套独立状态

- **原始核对**：OK / BAD / MISS 及差异数字始终保留。
- **审核**：未审核 / 审核通过 / 人工标异。审核通过退出「仅待处理异常」，人工标异（包括原始 OK）进入该筛选。原始 OK/BAD/MISS 统计不改，新增待处理、已审核、人工标异计数。
- **处理进度**：默认未处理，可选择处理中、已处理、未处理（重新打开），支持300字内备注与上海时区更新时间。已处理不等于审核通过，审核通过也不改变处理进度。处理筛选计数按全表统计，并与指标/搜索/待处理筛选取交集。

## 持久化与失效

业务键为公司代码 + 第三方期次 + 指标，独立于 `/admin/metrics` 的公告审核状态。
`metrics_check_reviews` 保存当前审核；`metrics_check_progress` 追加处理事件，不覆写/删除旧备注。服务端以实际原始输入（未四舍五入的值、单位、来源公告、第三方值、Q3涉及的H1伴随指标）和核对结论计算 SHA-256 快照。写入前以 repeatable-read 快照重算，页面已过时返回409而不是批准新数据。

当前数据与审核/处理事件的快照不符时，旧审核失效，处理进度显示未处理并保留上轮备注和更新时间；无实质变化重复解析不重开。备注后续修改为新事件，之前处理历史仍在服务端，暂不额外做历史工单界面。

表由既有 `ensureBackendSchema()` 以增量幂等方式创建，无需手动删除/重建现有数据。沿用开放后台，审核及处理不新增密码门，删除原有密码规则不变。前端不做批量解析。

## 验证边界

纯算法测试覆盖互切、序列化重读、数据变更、精度/单位/来源/H1失效、处理与审核独立、备注保存及SQL持久化契约；还需部署后用真实数据库和后台浏览器验收刷新持久化、实际解析进度。未对生产执行解析、审核或处理操作。
